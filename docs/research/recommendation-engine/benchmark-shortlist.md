# Benchmark shortlist: three learned MealRec variants

**Research specification · 2026-10-18 · no model training performed**

Ori's question is whether the engine can learn what someone wants, and whether weather and purchase history improve that prediction. I recommend comparing **regularized preference regression, CatBoost, and a context-aware factorization machine** on the same labels first. Add a temporal model only in a separate order-history experiment. These are distinct hypotheses about how preferences work, rather than three versions of the current fixed weights.

The [previous methodology study](prediction-methodology.md) explains the current engine and missing outcome logs. This note makes the algorithms, datasets, and comparison concrete. Dataset access was checked against public release endpoints on 2026-10-18; accessible files and permission to reuse them are reported separately.

## The three variants

For the first comparison, every model predicts the probability of a **high rating on a recipe that someone actually rated**. On a verified 1–5 scale, define `y = 1` for ratings 4–5 and `y = 0` for 1–3. Food.com's rating-zero semantics remain unaudited: retain only 1–5 for this task, and resolve the excluded values before interpreting them. “Lower rating” includes neutral responses and must not be renamed “dislike.” Freeze this conversion before model selection. Actual MealRec like/dislike events can later support their own binary task. Missing interactions remain unknown.

All three optimize binary log loss on identical retained events, initially with unit event weights. Several meals can receive high probabilities; these probabilities do not sum to one and are not single-choice probabilities.

| Variant | Concrete algorithm and implementation route | What it tests | Supporting study and limits |
| --- | --- | --- | --- |
| **M1 · Regularized personal preference** | L2 logistic regression over food attributes, user/item biases, prior taste compatibility, and a small declared set of crosses such as user×cuisine. Sparse features; scikit-learn logistic regression is a practical route. Shared weights provide the fallback for unseen users/items. | Whether readable, strongly regularized preferences already explain the signal; whether expensive models add anything. | [Fan et al., LIBLINEAR, JMLR 2008](https://www.jmlr.org/papers/v9/fan08a.html) establishes the sparse logistic approach. It is general classification evidence, not a food-choice study. |
| **M2 · Nonlinear context model** | CatBoostClassifier with `Logloss`; categorical IDs/cuisine plus numeric content, history, and available context. Start with shallow trees and tune depth, shrinkage, and tree count on development data. | Whether thresholds and nonlinear combinations matter: ingredient combinations on Food.com, or lunch/dinner patterns on timestamped order data. | [Prokhorenkova et al., NeurIPS 2018](https://proceedings.neurips.cc/paper/2018/hash/14491b756b3a51daac41c24863285549-Abstract.html) introduces ordered boosting and categorical statistics. Food or weather superiority is an untested transfer hypothesis. |
| **M3 · Collaborative/context interactions** | Second-order factorization machine: linear effects plus low-rank pairwise feature interactions. One sparse row per user–food–context event. The author's libFM supports logistic classification through **SGD**, with factor rank tuned on development data. | Whether shared patterns across users, foods, ingredients, and contexts outperform explicit crosses and trees. | [Rendle et al., Fast Context-aware Recommendations with Factorization Machines, SIGIR 2011](https://www.ismll.uni-hildesheim.de/pub/pdfs/Rendle_et_al2011-Context_Aware.pdf) directly studies contextual menu ratings, including hunger. Its rating-regression experiment differs from this proposed binary benchmark. |

**M1 needs a food-dependent personal signal.** A user intercept only measures how readily someone gives high ratings; it cannot change that person's ranking of meals. Include user×content effects or similarity between past preferences and the candidate's ingredients. Make those engineered signals available to all three models. The models receive the same raw information; their encodings and interaction structures differ.

Use ingredients/tags, available preparation time/nutrition, and strictly earlier feedback summaries where supplied. Food.com review dates do not establish lunch/dinner context. Do not assume public recipes have MealRec's exact cuisine, heaviness, or spice labels. Audit any mapping once and share it across models. Public user/item IDs do not identify MealRec users/meals.

Practical references: [scikit-learn logistic regression](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.LogisticRegression.html), [CatBoost classifier](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier.html), and [author libFM manual](https://www.libfm.org/libfm-1.42.manual.pdf). libFM's default MCMC classifier uses a probit link; explicitly choose `-task c -method sgd` for the sigmoid/logistic variant. During tuning, its required `-test` input must be development data. Never choose epochs using the final test output. Build/runtime compatibility was not tested.

LightFM is an optional static hybrid comparison, but its standard [interface](https://making.lyst.com/lightfm/docs/lightfm.html) supplies one feature row per user/item. It does not directly attach different weather to repeated events for the same user and food. An event-row FM represents that context naturally.

Food.com is associated with [Majumder et al., EMNLP 2019](https://aclanthology.org/D19-1613/) and its [author repository](https://github.com/majumderb/recipe-personalization). That paper benchmarks personalized **recipe generation**. We would reuse its data for a declared preference task; BLEU or generation results are not a recommendation baseline.

**Secondary sources:** [MealRec+ from SIGIR 2024](https://github.com/WUT-IDEA/MealRecPlus) supplies Allrecipes course reviews/metadata and constructed meal bundles. Raw course ratings could provide a second recipe domain after terms are resolved; constructed user–bundle interactions must not be presented as observed three-course purchases. This external dataset is unrelated to this app despite the shared name. [DHRD, RecSys 2023](https://github.com/deliveryhero/dh-reco-dataset), offers order/product/vendor data in three cities, but its linked Drive folder redirected to sign-in here. Its published schema uses relative order days; an absolute calendar anchor was not verified. Keep it conditional rather than promising a weather benchmark.

## A fourth variant when purchase history is available

**M4 · Repeat versus discovery model.** [Li et al., Right Tool, Right Job, RecSys 2024, author code](https://github.com/JiayuLi-997/FoodDeliveryRecommender) separates familiar-store recommendation (RepRec) from new-store recommendation (ExpRec), with an ensemble for a combined list. Its [preprint methods](https://arxiv.org/html/2402.14440v1) use TRD and DHRD, global chronological splits, and separate repeat/exploration evaluation. This is a particularly relevant next experiment for distinguishing habit from discovery. The published task recommends **stores**; applying it to dishes is an adaptation requiring its own evaluation. The preprint uses sampled candidates for exploration/combined ranking, so its scores are not full-catalog performance.

For a specifically **grocery next-basket** experiment, compare personal purchase frequency/recency, [TIFU-KNN, SIGIR 2020](https://github.com/HaojiHu/TIFUKNN), and [ReCANet, SIGIR 2022](https://github.com/mzhariann/recanet) on one frozen dataset. These provide an additional three-variant experiment, with a different target. Author code inspection found different nDCG normalization conventions and preprocessing gaps; use a shared evaluator rather than comparing paper headline scores. Instacart lacks absolute dates/location. Also distinguish dunnhumby's **Complete Journey** households from its **Let's Get Sort-of-Real** dummy-data sample; the [provider describes them separately](https://www.dunnhumby.com/source-files/).

## A fair comparison that answers the product question

### 1. Keep three leaderboards separate

- **Explicit preference:** M1–M3 on the same observed ratings. Primary measures: log loss and Brier score; also report calibration, PR-AUC, and both event-averaged and user-averaged results. Use the same unweighted training events; user-balanced evaluation exposes domination by prolific reviewers. Ranking only rated foods measures performance within that rated subset.
- **Observed purchase ranking:** adapt M1–M3 to the same TRD next-order target/candidates; optionally add M4 for the store target. Compare Recall@5/10 and standard nDCG@5/10, with repeat/new-item slices. If training contrasts purchases with sampled unpurchased candidates, declare the sampler and keep it identical. Those candidates are ranking contrasts, not verified dislikes; outputs are not calibrated willingness-to-eat probabilities. Keep all dishes in an order together.
- **Actual MealRec choice:** prospectively record eligible/displayed meals, context available then, a confirmed choice or explicit “none,” and later satisfaction when volunteered. Compare models on the same displayed alternatives. A hierarchical conditional/mixed-logit model becomes a distinct candidate for this single-choice likelihood; it cannot be validated by renormalizing public recipe-rating probabilities. Hierarchical binary logistic is also valid on ratings if partial pooling is worth testing.

### 2. Freeze the experiment before fitting

For Food.com, choose global earlier training, later development, and untouched final-test dates after auditing coverage. Fit feature vocabularies, scaling, and aggregates inside those boundaries. Keep a deterministic rule for multiple reviews of the same pair and report seen-pair versus new-pair performance. Exclude current review text and post-event popularity/nutrition summaries derived from outcomes. Use recipe metadata available by prediction time; if only a final snapshot exists, declare that limitation. For untimed Contextual Food/UCI, use grouped held-out ratings plus a separate unseen-user/item experiment and call it interpolation/cold start, not future prediction.

CatBoost's ordered statistics do not enforce the evaluation split or reconstruct past features. Apply its documented [time-order and categorical-statistic controls](https://catboost.ai/docs/en/references/training-parameters/common), and use development data for stopping. For UCI, exclude the other current-visit rating dimensions from predictors of overall rating.

For TRD, preserve March 22–28 as the test week; reserve March 19–21 for development and earlier dates for training, subject to the full-file audit. The actual headers differ from parts of its [README](https://zenodo.org/records/8025855/files/README.md?download=1): training dishes join through `wm_order_id` in a separate table. Exclude realized `order_price_interval`, supplied user payment averages, and venue rating aggregates unless their historical cutoff is established. Recompute allowable history from earlier events. The provided graph must not expose held-out order edges. Session clicks are a separate information ablation and must precede the prediction point.

Use training-only popularity, user+food biases, and content-only logistic controls; for purchases, add personal frequency/recency. Include the current heuristic only where its metadata can be mapped faithfully. Give all learned variants the same information, development-search budget, and candidate set. Record at least three seeds where training is stochastic, learning curves for short histories, and unseen-user/item coverage. A cold-start ID gets no untrained random embedding. Bootstrap paired differences by user; for weather claims, also assess uncertainty across time blocks. Select on development data once and report final-test uncertainty, runtime, memory, and maintenance burden.

### 3. Separate algorithm gains from extra-data gains

On a dataset with a valid join, run each model through the same four information conditions:

| Condition | Food content + clock/calendar | Personal history | Weather |
| --- | --- | --- | --- |
| D0 | Yes | No | No |
| D1 | Yes | Yes | No |
| D2 | Yes | No | Yes |
| D3 | Yes | Yes | Yes |

The no-history conditions must also remove learned personal-ID effects and personal taste profiles. Otherwise they already contain history. Purchase-derived item, cuisine, recency, and budget summaries must use strictly prior events; ordinary bank transaction categories do not supply dish identities. Public datasets cannot provide another person's private purchase history for a MealRec user.

TRD supports only a **coarse retrospective weather pilot**: verify `dt`/timestamp conversion to Asia/Shanghai, join Beijing hourly weather, and test food×weather interactions while controlling for calendar/time. In a linear score, a common weather term alone leaves relative food rankings unchanged; food-dependent interactions allow weather to change the order. A sampled 77 complete order rows agreed with local dates; a complete join audit remains necessary. The [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api) supplies reanalysis, which was produced after the original decisions. Label it retrospective explanatory input. An operational prediction needs weather available at that moment; a next-meal forecast needs a forecast issued beforehand, with availability lag respected ([single-run documentation](https://open-meteo.com/en/docs/single-runs-api)). No 2021 issue-time forecast archive was verified here. Do not use realized full-day rain/maximum temperature for a morning prediction.

Weather is shared across many users in the same hour/day. A large order count does not create many independent weather observations. This 28-day sample needs time-block uncertainty, and a gain can still reflect calendar/platform conditions rather than a transportable weather effect. Food.com, Contextual Food, UCI, and Instacart cannot fix this by attaching invented locations/dates.

## Recommended starting scope

Start with **M1 versus M2 versus M3 on one Food.com preference task**, conditional on suitable data terms; use UCI for a small openly licensed sanity check and Contextual Food for a hunger ablation. Then run a distinct TRD purchase-ranking experiment, with weather as an exploratory data ablation. Add RepRec/ExpRec only if the store-repeat/discovery question matters. Strong results should justify a prospective MealRec trial; public benchmarks alone do not establish that the engine predicts what Ori's users want.

Verified here: primary papers/repositories, named public access routes, selected file headers/small samples, and task compatibility. Not performed: full corpus validation, dependency builds, model fitting, weather joins, or a MealRec user study. None of the proposed variants has a measured advantage in this project.
