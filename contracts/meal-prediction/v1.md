# Meal-prediction export contract, version 1

This is the local JSON boundary between the opt-in pilot exporter and the offline
benchmark. `pilot-v1.example.json` is a **synthetic test-only fixture**. It contains
no participant observations or live weather and must never enter an empirical
pilot result. Public-data adapters construct Python records directly; they must
not fabricate pilot visits, timestamps, hunger, or weather.

## JSON rules

The envelope has exactly these required fields:

| Field | Value |
| --- | --- |
| `schemaVersion` | Integer `1`, never a boolean |
| `source` | `"pilot"` |
| `manifest` | `ExportManifest` below |
| `participants` | Array of `ParticipantView` |
| `visits` | Array of `VisitRecord` |
| `allocations` | Array of `CardAllocation`, including unshown allocations |
| `exposures` | Array of `ExposureRecord`, in retained export order |
| `responses` | Array of immutable `ResponseRecord` |
| `audit` | Array of `{eventId: string, reason: string}` |

Every field listed below is required, including fields whose value may be
`null`. Unknown fields and invalid types are rejected. All IDs are nonempty
strings, unique within their entity array. IDs identify study-specific
pseudonymous participants; no username, user ID, PIN/hash, session, identity
mapping, database URI, or provider credential belongs in the export.

`UTC` below means an ISO-8601 string with a zero UTC offset, such as
`2026-01-02T12:01:00Z` or `2026-01-02T12:01:00+00:00`. Naive/local timestamps
are invalid. Python parses known instant fields into aware UTC `datetime`
objects. IANA zone names remain strings; `localDate` remains `YYYY-MM-DD`.
All numerics must be finite; numeric fields reject booleans. Arrays of strings
contain nonempty strings. Optional context is represented by explicit `null`,
never inferred from a missing field or silently substituted with a default.

## Study and export manifest

`StudyConfig` has `studyId`, `studyVersion`, `protocolVersion`, `catalogVersion`
(nonempty strings), `catalogSha256` (lowercase 64-digit SHA-256 hex), `startsAt`
(UTC), `seed` (nonnegative integer), and `cityOptions` (`CitySelection[]`).
`StudyRecord` adds `schemaVersion: 1`, `trainingEndsAt`, `developmentEndsAt`,
`endsAt` (UTC), and `quotaTimezoneRule: "enrollment"`.

`ExportManifest` contains all `StudyRecord` fields **except `cityOptions`** and
adds:

| Field | Value |
| --- | --- |
| `phase` | `"development"` or `"final"` |
| `exportedAt` | UTC export time |
| `sourceProvenance` | `{name: string, url: string \| null, license: string, attribution: string}` |
| `freezeLink` | `FreezeLink` for final exports; `null` for development exports |

The fixed boundaries are `trainingEndsAt = startsAt + 5 days`,
`developmentEndsAt = startsAt + 7 days`, and `endsAt = startsAt + 14 days`.
The intervals are half-open: training `[startsAt, trainingEndsAt)`, development
`[trainingEndsAt, developmentEndsAt)`, and test `[developmentEndsAt, endsAt)`.
The enrollment timezone governs daily quota throughout the study; the current
visit city timezone governs local prediction context. The catalog hash names
the frozen catalog input, rather than today's mutable catalog.

`FreezeLink` has `freezeManifestSha256`, `developmentSnapshotSha256`
(lowercase SHA-256 hex strings) and `frozenAt` (UTC). These link the final export
to the separately persisted freeze manifest and exact development-snapshot
bytes. The loader checks their shape, not the existence or contents of those
artifacts; fit/freeze/scoring code verifies the actual hashes. Exporters must
omit second-week records from development exports. The loader rejects display
acknowledgements or server response receipts at/after `developmentEndsAt` in a
development snapshot. Freeze timing/prospective status is assessed by the later freeze/evaluation workflow.

## Participants and settings

`CitySelection` has `cityId`, `label`, `country` (strings), `adminArea`
(string or `null`), `latitude` (number from -90 to 90), `longitude` (number from
-180 to 180), and `timezone` (IANA zone). Store this selected place, including
its coordinates, rather than resolving today's city label again.

`EnrollmentSettings` has `version` (positive integer), `effectiveAt` (UTC),
`city` (`CitySelection`) and `dietaryExclusions` (string array). Versions are
unique within a participant. Changes apply prospectively; retain the history.

`ParticipantView` has `participantId` (string), `enrolledAt` (UTC),
`enrollmentTimezone` (IANA zone) and `settings` (nonempty
`EnrollmentSettings[]`). It contains no authentication identity.

## Visits and raw weather

`VisitRecord` has:

| Field | Value |
| --- | --- |
| `visitId`, `participantId` | Stable ID and participant reference |
| `settingsVersion` | Existing positive settings version for that participant |
| `startedAt`, `expiresAt`, `contextCapturedAt` | UTC instants |
| `city` | `CitySelection` matching the referenced settings version |
| `hunger` | `"not_hungry"`, `"somewhat_hungry"`, `"very_hungry"`, or `null` |
| `weather` | `WeatherSnapshot` or `null` |

The visit context is immutable. A valid visit has positive duration at most
thirty minutes. Weather capture/availability policy is implemented separately:
three-second timeout, maximum age one hour, maximum future offset five minutes.
Failed or stale context does not remove an otherwise valid definite response.
The loader preserves the raw snapshot; it does not fetch or backfill weather,
reinterpret unfamiliar condition codes, or turn failure into normal weather.

`WeatherSnapshot` has exactly:

| Field | Value |
| --- | --- |
| `provider`, `providerHost`, `accessMode` | String or `null`; provenance without credentials |
| `status` | `"ok"`, `"partial"`, or `"unavailable"` |
| `requestedLatitude`, `requestedLongitude` | City coordinates; numbers in latitude/longitude bounds |
| `gridLatitude`, `gridLongitude` | Returned grid coordinates in bounds, or `null` |
| `validAt` | Weather-valid UTC time or `null` |
| `sourceIntervalSeconds` | Integer source interval or `null` |
| `requestedAt` | Application request/attempt UTC time |
| `retrievedAt` | Application retrieval UTC time or `null` |
| `temperatureC`, `precipitationMm` | Finite number or `null`; zero is a value |
| `weatherCode` | Integer raw WMO code or `null`; unfamiliar codes are retained |
| `units` | `{temperature: "celsius", precipitation: "mm"}` |
| `sourceTimeFormat` | `"unixtime"`, describing provider timestamps before UTC serialization |
| `timezone` | Provider-returned IANA zone or `null` |
| `failureReason` | String or `null` |

Retrieval time is neither weather-valid time nor model issuance/station
observation time. Provider host/access mode are launch inputs. Source attribution
belongs in the export provenance; the collector is responsible for presenting
Open-Meteo/GeoNames attribution when those sources are used.

## Allocations, exposures, and responses

`CardAllocation` has `allocationId`, `participantId`, `itemId` (strings),
`localDate` (quota date), `settingsVersion` (existing positive participant
settings version), `allocatedAt` (UTC), `eligiblePoolSize` (positive integer),
and `selectionProbability` (number in `(0, 1]` recorded by the allocation
process). Allocations preserve the draw independently of display or answer;
selection probability is not a training weight. Replaced/unshown allocations
remain representable with their own stable IDs.

`MealSnapshot` has `id`, `name` (strings); `cuisine`, `imageUrl`, `description`
(string or `null`); `primaryIngredients`, `allergens`, `weather`, `timeOfDay`,
`flavorTags` (string arrays); and `spiciness`, `heaviness` (numbers from 0 to 5).
It is the meal content at exposure time. `id` is a string, not a database object.

`ExposureRecord` has `eventId`, `participantId`, `visitId`, `allocationId`,
`itemId` (strings), `settingsVersion` (matching its visit), `displayedAt`,
`clientDisplayedAt` (UTC), and `meal` (`MealSnapshot`). `displayedAt` is the
**server acknowledgement of display**, the prediction point.
`clientDisplayedAt` is the separate raw client display clock. One allocation
can create at most one acknowledged exposure; retries reuse its stable ID.
Participant ownership must agree across the visit, allocation, and exposure.
`itemId` must agree with the allocation and meal snapshot's `id`.

`ResponseRecord` has `responseId`, `eventId`, `participantId` (strings),
`answer` (`"yes"`, `"no"`, `"not_sure"`), `actionAt` (raw client action UTC)
and `receivedAt` (server receipt UTC). The response participant must own the
exposure. Duplicate response IDs and multiple responses for one event are
invalid, including a conflicting second answer. Retry handling belongs in the
collector and returns the original record. Legacy feedback outcomes are not
part of this protocol.

## Python labels, alignment, and audit

The frozen records are:

- `Exposure(event_id, participant_id, item_id, displayed_at, meal, context)`;
  no response/outcome fields. `context` retains the parsed visit, allocation
  metadata, enrollment timezone, referenced dietary exclusions, and raw client
  display time. Meal/context dictionaries preserve nullable raw values.
- `Target(event_id, y, received_at)`, with integer `y` restricted to `0` or `1`.
  Booleans and nonfinite/nonbinary values are invalid.
- `AuditEntry(event_id, reason)` and
  `Dataset(source, manifest, events, targets, audit)`. `events` is an ordered
  tuple, `targets` maps event IDs to `Target`, and `audit` is an ordered tuple.
- `Split(train_ids, development_ids, test_ids, audit)` stores ordered ID tuples.
- `FeatureBatch(ids, participant_ids, rows, events)` stores aligned tuples;
  `rows` contains dictionaries with string keys and float/string values.
  Candidate adapters receive only `rows`; metadata/events are for alignment,
  evaluation, and the reference control. No label is stored in a feature batch.

Public records use `None` for unavailable display/receipt times. Pilot JSON
requires its explicit timestamps. Record freezing prevents attribute assignment;
meal/context/manifest dictionaries remain ordinary dictionaries.

`load_snapshot(path: Path) -> Dataset` validates the envelope, exact fields,
values, IDs, ownership, settings references and fixed cutoffs. It preserves all
exposures. `yes` maps to `1`, `no` to `0`; `not_sure` and unanswered events
produce `not_sure`/`unanswered` audit entries and **no binary target**. Imported
audit reasons are retained; uncertainty is never recoded as a negative.

The loader also excludes definite responses from binary labels while retaining
the exposure and fixed audit reasons for:

- `invalid_visit_interval`: visit duration is nonpositive or over thirty minutes.
- `display_outside_visit`: acknowledgement is before visit start or at/after expiry.
- `display_outside_study`: acknowledgement is outside the study's half-open window.
- `response_before_display`: server receipt is at/before acknowledgement.
- `response_after_visit`: server receipt is at/after visit expiry.
- `response_outside_study`: receipt is outside the study's half-open window.
- `crosses_cutoff`: display and receipt belong to different fixed intervals.

Client clocks never replace server acknowledgement or receipt for primary
eligibility. Raw client times remain available for audit. All three candidates
share these exclusions before fitting/scoring.

`events_for(dataset, ids) -> tuple[Exposure, ...]` and
`labels_for(dataset, ids) -> numpy.ndarray` preserve the requested ID order.
Unknown IDs fail with `ValueError`; requesting a missing/uncertain/excluded
label also fails, rather than fabricating a zero. Every retained fitting event
has unit weight. Participant-balanced scoring belongs to evaluation code.

`ActionResult<T>` is the collector-facing tagged union
`{ok: true, value: T}` or `{ok: false, error: {code: string, message: string}}`.
It is not part of the export envelope. The TypeScript definitions live in
`packages/database/src/pilot/types.ts`; no database access is needed by Python.

## Local environment and ignored artifacts

From `benchmarks/meal_prediction`, install with `uv sync --frozen`, run checks
with `uv run --frozen python -m pytest`, and use `uv run --frozen python ...` for
subsequent commands. The project requires Python 3.12, uses `tool.uv.package=false`,
and locks NumPy, scikit-learn, CatBoost, River and pytest in `uv.lock`. The
benchmark uses CPU only; candidate code must select CPU execution.

Keep downloaded inputs and raw pilot snapshots under
`benchmarks/meal_prediction/data/` or `raw-exports/`; keep generated runs and
models under `runs/` and `models/`. Those locations, virtual environments, and
Python caches are ignored. Code, the lock, and this compact synthetic fixture
remain tracked. This contract adds no database credentials, adapter, feature,
model, collector, export CLI, or empirical result.
